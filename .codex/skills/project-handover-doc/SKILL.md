# 项目交接文档

生成一份可直接粘贴给新 AI 的项目交接文档，目标是让新窗口里的 AI 在没有当前会话上下文的情况下，也能继续开发、排查和验证。

默认输出中文，优先写“当前仓库真实状态”，不要写空泛总结，不要把猜测写成事实。

## 执行流程

### 1. 先确认当前事实

- 先看 `git status --short`，确认是否有未提交改动，避免把工作区说错。
- 再看当前分支、最近提交、关键目录和实际运行入口。
- 优先核对：
  - `server/` 后端与插件入口
  - `saiadmin-artd/` 管理端
  - `uniapp/` 移动端
  - `packages/` 扩展包
  - `Database/`、`Doc/`、`OpenAPI/`
  - `.env.example`、配置目录、部署脚本
- 对“是否已验证”必须找证据：命令输出、构建结果、路由、日志、页面访问、迁移状态、实际文件变更。

### 2. 按模块梳理状态

- 不要只按目录罗列，要按“功能模块/业务模块/基础设施模块”组织。
- 每个模块至少说明：
  - 状态：已完成 / 开发中 / 已验证 / 未验证 / 已废弃 / 不确定
  - 相关文件
  - 核心逻辑
  - 当前问题
  - 下一步
- 明确区分：
  - 已完成且验证过
  - 已写代码但未验证
  - 写到一半
  - 后来放弃
  - 已证明不可行，不要重复尝试

### 3. 写清楚“为什么这样实现”

- 核心逻辑说明不要只贴代码。
- 解释请求入口、数据流转、关键类/函数、设计原因、改动历史、临时方案和技术债。
- 新 AI 需要知道：
  - 哪些地方能安全改
  - 哪些地方一改就可能牵一发动全身
  - 哪些逻辑是为了兼容历史，哪些是当前新规范

### 4. 处理敏感信息

- 遇到 API Key、Token、Cookie、密码、私钥、数据库口令、第三方密钥时，不输出真实值。
- 统一写成 `[REDACTED]`。
- 示例值只写格式，不写真值。

### 5. 标注不确定项

- 任何没有证据的内容都标注“不确定”。
- 不要因为文档结构要求完整，就编造“已部署”“已验证”“已上线”“已支持”。
- 如果命令没跑、页面没开、接口没测、数据库没查，就明确写未验证或不确定。

## 输出要求

- 严格按 `references/handover-template.md` 的九大章节输出。
- 以“能让新 AI 直接接手”为标准，不要写成面向人类管理层的周报。
- 优先写高价值事实：
  - 当前状态
  - 文件落点
  - 风险和坑
  - 后续路径
- 少写空话：
  - 避免“项目结构清晰”“功能基本完善”“具备一定可维护性”之类表述。

## 当前仓库的额外要求

- 默认遵守当前仓库 `AGENTS.md` 和本地规范。
- 如果这是 B8AIadmin / SaiAdmin / Webman 系项目，交接文档里优先说明：
  - 插件模式与真实路由入口
  - Phinx 迁移与数据库基线
  - 后端 `server/`、前端 `saiadmin-artd/`、移动端 `uniapp/` 的关系
  - 是否依赖 Webman 常驻进程 reload/restart
  - 是否修改过 `packages/` 并影响运行时
- 如果当前会话里已经做过修复、验证或结论，把这些结论写进“最近修改记录”和“已知问题与坑”，但只写已确认事实。

## 最低检查清单

输出交接文档前，尽量覆盖以下检查项；缺失时明确写未检查：

- `git status --short`
- 当前分支名
- 关键目录结构
- 主要依赖定义文件
- `.env.example` 或配置示例
- 路由/接口入口
- 数据库迁移或安装资料
- 构建/启动/测试命令
- 部署脚本或部署说明
- 最近改动文件和验证结果
